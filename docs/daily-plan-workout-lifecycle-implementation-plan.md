# 当天动态计划训练单实施计划

## 实施原则

1. 先增加兼容字段和领域逻辑，再切换 API 与前端，不删除现有训练数据。
2. “当天完成”和“历史冻结”使用独立字段与判断，不再让 `completed_at` 同时承担两种语义。
3. 计划日和计划动作 ID 必须稳定；当天训练对账只使用 ID，不根据名称、位置或动作库 ID 猜测。
4. 计划对账必须幂等，可以在保存计划、读取今日状态和重试时重复执行。
5. 后端按 `Asia/Shanghai` 时区控制跨日边界，前端刷新仅用于改善体验。

## 阶段 1：领域模型与可测试规则

### 目标

先将日期、完成状态和动作差异计算从路由中抽离，避免在数据库代码中边写边猜业务规则。

### 改动

- 新增 `lib/daily-workout-domain.ts`：
  - 计算上海业务日期和下一个零点。
  - 判断训练单是否已冻结。
  - 计算计划动作与训练快照之间的 `add / restore / remove / update / keep` 差异。
  - 根据未删除且未完成动作计算 `not_started / in_progress / completed / finalized` 状态。
  - 计算当前动作，不允许 `undefined === undefined` 类似的空值命中。
- 扩展 `lib/training.ts`：
  - 为训练会话增加业务日期、当前完成、冻结、已累计时长和当前计时段起点类型。
  - 为训练动作增加从计划移除的状态。
  - 增加今日页可直接消费的训练状态类型。

### 测试

- 新增 `tests/daily-workout-domain.test.ts`，用 Node 22 内建测试和 TypeScript strip-types 能力执行纯函数测试。
- 覆盖上海时区日期边界、新增动作、删除未完成动作、删除已完成动作、恢复动作和全部完成场景。
- 修改 `package.json` 的 `test` 脚本，在生产构建后运行现有测试与新领域测试。

### 验收

- 领域函数不依赖 React、D1 或系统当前时区。
- 所有动作成员变化都能通过输入、输出测试确认。

## 阶段 2：数据库增量迁移

### 改动文件

- `db/schema.ts`
- `db/index.ts`
- `drizzle/0002_*.sql` 及 `drizzle/meta/*`

### 训练会话字段

在 `workout_sessions` 增加：

- `workout_type TEXT NOT NULL DEFAULT 'plan'`：为后续计划外训练预留类型边界。
- `training_date TEXT`：上海时区 `YYYY-MM-DD` 业务日期；旧历史允许为空。
- `finalized_at INTEGER`：训练快照冻结时间。
- `synced_plan_version INTEGER`：最后成功同步的计划版本。
- `resumed_at INTEGER`：当前活跃计时段起点；暂时完成时为空。

复用现有 `duration_seconds` 保存已累计的实际训练时长：

- 首次开始：`duration_seconds = 0`，`resumed_at = started_at`。
- 当天暂时完成：将当前计时段追加到 `duration_seconds`，清空 `resumed_at`。
- 新增动作后恢复：`resumed_at = now`，不将中间休息的数小时计入训练时长。
- 跨日冻结：计时段最多截止到下一个上海零点。

### 训练动作字段

在 `workout_exercises` 增加：

- `removed_from_plan_at INTEGER`：该动作从当天最新计划移除的时间，与 `skipped` 保持独立。

### 索引与兼容

- 为新计划训练增加用户、业务日期和训练类型的唯一索引，仅限 `training_date IS NOT NULL AND workout_type = 'plan'` 的记录。
- 为 `workout_session_id + plan_exercise_id` 增加非空部分唯一索引，防止重复追加动作。
- 旧已完成训练保持 `training_date = NULL`、`finalized_at = completed_at`，不受新的单日唯一性限制。
- 旧进行中训练按 `started_at` 换算业务日期：当天的进入新流程，过期的立即冻结。
- `db/index.ts` 的运行时补列逻辑必须与 Drizzle 迁移保持一致，支持现有部署原地升级。

### 验收

- 迁移可在空库和含旧数据的库上执行。
- 不删除任何旧训练组、训练动作或历史会话。
- 多设备并发创建时由数据库阻止重复当天训练单。

## 阶段 3：计划日与动作稳定 ID

### 改动文件

- `app/api/plans/active/route.ts`
- `lib/server/plans.ts`
- `components/training-plan-view.tsx`

### 后端改动

- `parsePlan` 保留已存在的训练日 ID 和动作 ID，不为每次保存重新生成全部 ID。
- `replaceActivePlan` 从“删除全部训练日后重建”改为差异更新：
  - 更新仍存在的训练日和动作。
  - 插入新增训练日或动作。
  - 最后删除输入中已不存在的动作。
  - 周计划仍使用 `version` 乐观锁。
- 验证所有旧 ID 确实归属当前用户和当前计划。
- 新 ID 如与其他用户或其他计划冲突，返回稳定错误，不覆盖数据。

### 前端改动

- 新增训练日或动作时只生成一次 UUID。
- 排序、修改字段和重复保存不替换 ID。
- 保存成功后使用服务端返回的计划替换本地草稿基线，避免继续携带旧版本号。

### 测试

- 连续保存同一计划两次，断言未删除训练日和动作 ID 不变。
- 新增动作只有新动作获得新 ID。
- 旧版本并发保存返回 `409 CONFLICT`。
- 伪造他人计划动作 ID 不能插入当前计划。

## 阶段 4：当天训练对账服务

### 改动文件

- `lib/server/workouts.ts`
- `lib/server/plans.ts`
- `lib/server/dashboard.ts`

### 新增服务能力

- `finalizeExpiredPlanWorkouts(userId, now)`：
  - 查找业务日期早于今天的未冻结计划训练。
  - 将活跃计时段截止到对应业务日结束时间。
  - 写入 `finalized_at`，保留当时完成或未完成状态。
- `getTodayPlanWorkout(userId, now)`：
  - 先惰性冻结过期训练。
  - 返回当天训练，即使它当前已完成，也不会像现在一样查询不到。
- `reconcileTodayPlanWorkout(userId, plan, now)`：
  - 没有当天训练时直接返回，不因保存计划自动开始训练。
  - 对比当天计划动作和训练快照。
  - 追加新动作，恢复被重新加回的动作，标记已移除动作。
  - 只在安全时同步未完成快照的配置。
  - 根据剩余待完成动作重算会话 `completed_at`。
  - 从已完成恢复为进行中时设置 `resumed_at = now`。
  - 同一计划版本重复调用时不产生新写入。
- `recalculatePlanWorkoutCompletion(workoutId, now)`：
  - 只统计 `removed_from_plan_at IS NULL AND completed_at IS NULL` 的动作。
  - 无待完成动作时结算当前计时段并进入暂时完成。
  - 仍有待完成动作时保持进行中。

### 计划保存与对账一致性

- 优先将计划差异写入和当天训练对账语句组装进同一次 D1 `batch`，防止出现“计划已保存，但今日训练没同步”的中间状态。
- 如果现有 D1 调用边界无法将全部查询与写入放在单次批处理中，则保存计划后执行幂等对账，并让今日读取再次修复；接口必须返回服务端最终状态，不得伪报本地完成。

### 验收

- 对账函数重复执行不产生重复动作。
- 删除已有训练组的动作不会删除组记录。
- 完成后数小时再新增动作，中间等待时间不计入训练时长。

## 阶段 5：训练 API 状态改造

### 改动文件

- `app/api/workouts/route.ts`
- `app/api/workouts/active/route.ts`
- `app/api/workouts/[id]/sets/route.ts`
- `app/api/workouts/[id]/exercises/[exerciseId]/complete/route.ts`
- `app/api/workouts/[id]/complete/route.ts`
- `app/api/plans/active/route.ts`
- `app/api/dashboard/route.ts`

### 创建与查询

- `POST /api/workouts`：
  - 创建前惰性冻结过期训练。
  - 如果当天已有计划训练，不创建第二条。
  - 已完成且无新动作时返回稳定冲突码 `TODAY_PLAN_COMPLETED`。
  - 存在待完成动作时返回已存在训练，客户端进入继续流程。
- `GET /api/workouts/active`：
  - 保留路由以减少前端改动，但返回结构增加 `status`。
  - 进行中返回完整 workout。
  - 当天已完成返回训练摘要和 `completed` 状态，而不是直接返回 `null`。
  - 当天无训练返回 `not_started`。

### 写入保护

- 保存组、完成动作、跳过和暂时完成接口在写入前统一检查：
  - 用户归属。
  - `workout_type = 'plan'`。
  - `training_date` 等于当前上海日期。
  - `finalized_at IS NULL`。
  - 动作没有从当前计划移除。
- 跨日写入返回稳定错误码 `WORKOUT_FINALIZED`，前端据此退回今日页。
- 完成最后一个动作后由服务端重算会话状态，不依赖前端再额外判断一次是否完成整场。
- `POST /api/workouts/:id/complete` 改为幂等的当天暂时完成确认，或在服务端自动重算后保留为兼容路由；它不写入 `finalized_at`。

### 计划保存返回

- `PUT /api/plans/active` 在保存成功后返回：
  - 服务端最新计划。
  - 对账后的当天训练状态。
- 前端不需要等待第二次请求才判断按钮是“已完成”还是“继续”。

### 验收

- 当天重复点击开始、快速连点或两个设备同时开始，都不产生重复训练单。
- 已完成当天训练时无法通过手工 API 再创建一条同类训练。
- 已冻结训练无法保存新训练组。

## 阶段 6：今日页与训练页状态接入

### 改动文件

- `app/page.tsx`
- `components/active-workout-view.tsx`
- `app/globals.css`

### 启动与恢复状态

- 应用启动时读取当天训练状态，不再只保存 `ActiveWorkout | null`。
- 前端保存明确的 `todayWorkoutStatus`：
  - `not_started`
  - `in_progress`
  - `completed`
- 只有 `in_progress` 自动进入或允许进入训练页。
- 刷新页面时，当天暂时已完成训练不再直接进入训练页。

### 今日动作列表

- 继续使用稳定计划动作 ID 将计划项与训练快照映射。
- 状态优先级：`completed -> current -> pending`。
- 没有训练单或没有对应快照时只能是 `pending`，不得因为两边都为空而命中 `current`。
- 已从计划移除的未完成快照不在当前计划列表显示。

### 底部状态

- `not_started`：显示现有亮绿色“开始训练”。
- `in_progress`：显示“继续 {currentExerciseName}”，点击后滚动并定位到当前动作。
- `completed`：替换为不可点击的“今日训练已完成”状态：
  - 保留底部可见性，但降低攻击性色彩。
  - 不绑定开始请求。
  - 新增动作后服务端返回 `in_progress`，原位转为“继续”。

### 训练时长

- 训练页计时从 `durationSeconds + (now - resumedAt)` 计算，不再单纯使用 `now - startedAt`。
- 当天完成后新增动作，重新进入时从新的活跃计时段继续累计。
- 训练页中保存组或完成动作收到 `WORKOUT_FINALIZED` 时，立即清理休息层、退回今日页并重载服务端状态。

### 跨日刷新

- 页面持续打开时计算到下一个上海零点的剩余时间。
- 跨日后清理昨日进行中 UI，重新读取今日计划和训练状态。
- 定时刷新不取代服务端写入保护。

### 验收

- 全部完成后今日页不再出现可点击的开始按钮。
- 新增动作后无需刷新页面就显示继续状态。
- 删除最后一个未完成动作后立即显示完成状态。

## 阶段 7：统计、历史与兼容查询

### 改动文件

- `lib/server/dashboard.ts`
- `lib/server/workouts.ts`
- 必要时的页面类型映射

### 查询规则

- 已完成训练动作被从当前计划删除后，其训练组仍参与容量和 1RM 统计。
- 被移除且从未完成的动作不计入完成动作数。
- 当天暂时已完成训练可显示在近期训练中；如果因新增动作恢复为进行中，在再次完成前不作为已完成训练展示。
- 训练次数、连续天数和活跃周按业务日期去重，不因当天重新打开而重复计数。
- 旧历史数据仍按现有 `started_at / completed_at` 逻辑兼容读取。

### 验收

- 同一天完成、新增动作、再完成的过程最终只计一次训练。
- 被删除的已完成动作仍保留训练容量和趋势数据。
- 旧用户的近期训练、训练频率和力量趋势不丢失。

## 阶段 8：验证与回归

### 自动验证

1. `npm run lint`
2. `npm test`
3. `npm run db:generate`，检查迁移内容不包含非预期删表或数据丢失操作。
4. `git diff --check`
5. 检查 D1 运行时补列逻辑与 Drizzle schema 字段、索引一致。

### 服务端场景验证

1. 新用户开始当天计划，完成全部动作后无法再创建第二条。
2. 完成后新增动作，原训练单恢复为进行中且只追加一个动作。
3. 完成 5/6 后删除未完成动作，会话进入已完成。
4. 删除已完成动作，已保存组数不变。
5. 相同计划版本对账两次，训练动作数量不变。
6. 伪造昨日训练写入请求，返回 `WORKOUT_FINALIZED`。
7. 两个并发开始请求最终只保留一条当天计划训练。
8. 迁移前已完成训练仍能被 dashboard 读取。

### 前端代码级检查

- 不进行耗时的动画视觉自动化，按用户已确认的方式只检查报错、状态转换和代码逻辑。
- 确认底部操作只有一个状态源，不会同时显示“开始”与“已完成”。
- 确认新增动作后使用服务端返回状态，不使用本地乐观猜测。
- 确认页面卸载时清理跨日定时器和训练计时器。

## 主要风险与控制

### 风险 1：稳定 ID 改造导致计划保存丢数据

- 先读取当前 ID 集合并验证归属。
- 在一次批处理中先更新或插入，最后删除已移除项。
- 加入连续保存与并发版本测试。

### 风险 2：训练完成后恢复导致时长虚高

- 引入 `resumed_at` 并累加活跃时段，不使用从首次开始到最终完成的整段墙上时间。
- 服务端结算，不信任客户端传入的总时长。

### 风险 3：跨日后页面仍向昨日训练写入

- 所有写接口共用同一个可写性检查。
- 前端跨日刷新和后端 `WORKOUT_FINALIZED` 保护双重兜底。

### 风险 4：旧数据与新唯一索引冲突

- 旧已完成训练不回填 `training_date`，避免历史上同日多次训练阻断迁移。
- 新唯一索引只覆盖新流程中业务日期非空的计划训练。

## 完成定义

以下条件全部满足时，本次改造才算完成：

1. spec 中 12 个验收场景均有实现或自动测试覆盖。
2. 当天训练完成后无法重复开始，新增动作后可继续原训练。
3. 删除剩余未完成动作可使当天训练进入完成状态。
4. 已完成的动作和训练组不因计划删除而丢失。
5. 零点后昨日训练无法继续写入，且后续计划变更不影响昨日快照。
6. 现有用户、计划、训练和统计数据在迁移后仍可正常读取。
7. Lint、生产构建、自动化测试、迁移检查和 `git diff --check` 全部通过。
